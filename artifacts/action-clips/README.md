# Action clips: crouch / crawl / jump

ARDY-generated action clips for the gmgn action stack, plus the numbers that
say which ones are usable. Generated by
[`scripts/ardy_actions.py`](../../scripts/ardy_actions.py); the machine-readable
record is [`manifest.json`](manifest.json).

**Nine clips are generated; six are in the preview grid.** The six grid cells are
the original set; the scope then narrowed to **the jump only**, which added
`jump_air` and `jump_forward` (see [§8](#8-the-jump--跳--this-rounds-narrowed-scope))
and their own 3×1 GIF, [`preview_jump.gif`](preview_jump.gif). The seventh,
`stand_idle_zh`, is a Chinese-vocabulary baseline that is deliberately not in any
grid.

**What is committed here:** `manifest.json`, `foot-skating.json`,
`text-vectors.json`, `prompts.txt`, `preview.gif`, `preview.json`,
`preview_jump.gif`, `preview_jump.json`, this README.
**What is not:** the clips themselves. `artifacts/action-clips/raw/**` is
weight-derived and git-ignored (`.gitignore`), same rule as
`artifacts/golden-run*/{raw,out}`.

---

## 一键重生成 / One command to regenerate

```bash
cd ~/dev/ardy-mlx
./.venv/bin/python scripts/ardy_actions.py all
```

That runs four steps in order, each of which also works alone:

| Step | What it does | Cost |
|---|---|---|
| `encode` | encodes the nine prompts into the embedding cache via the sibling `~/dev/llm2vec-mlx` encoder | ~3 s warm, ~4 s/prompt cold |
| `generate` | runs `scripts/ardy_generate.py --backend mlx` **twice per action** (postprocessing on / off), measures foot skating and the jump's vertical profile, writes `manifest.json` | ~15 s for six actions, **32 s for all nine** |
| `preview` | composes the 3×2 labelled GIF | ~10 s |
| `preview-jump` | composes the 3×1 jump-only GIF, `preview_jump.gif` | ~6 s |

Nothing is installed and no system dependency is added: the encoder is the
sibling checkout's own `.venv`, and the only external binary is `ffmpeg`, which
this repository's preview path already required.

Individual steps:

```bash
./.venv/bin/python scripts/ardy_actions.py encode
./.venv/bin/python scripts/ardy_actions.py generate
./.venv/bin/python scripts/ardy_actions.py preview --cell-width 300 --cell-height 320 --fit-frames 40 --fps 10 --max-colors 64
./.venv/bin/python scripts/ardy_actions.py preview-jump --cell-width 300 --cell-height 320 --fit-frames 40 --fps 10 --max-colors 64
```

## 1. The six actions / 六个动作

Prompts are third person, matching the viewer's own vocabulary. Every clip uses
the same checkpoint, seed, step count and guidance, so **the only thing that
differs between them is the text vector** — the six clips are six rollouts from
the same initial noise.

| name | prompt | duration | frames |
|---|---|---|---|
| `stand_idle` | `A person stands still.` | 2.0 s | 40 |
| `crouch_idle` | `A person crouches down and stays crouched.` | 2.0 s | 40 |
| `crouch_forward` | `A person crouches and walks forward slowly.` | 4.0 s | 80 |
| `crawl_forward` | `A person crawls forward on hands and knees.` | 4.0 s | 80 |
| `jump` | `A person jumps up in place and lands.` | 2.0 s | 40 |
| `walk` | `A person walks forward.` | 4.0 s | 80 |
| `jump_air` | `A person jumps up in the air and lands on the spot.` | 2.0 s | 40 |

`20 fps`, `horizon 40`, `D = 330` (motion representation), `J = 27` (joints).

## 2. Foot skating / 脚滑

### What was measured, and how

A foot **skates** when the contact point travels across the ground while it is
supposed to be planted. So for each of the four contact joints
(`LeftFoot, LeftToeBase, RightFoot, RightToeBase`, contract S1.5 order):

* it is *planted* at frame `t` when its own `foot_contacts` channel is true at
  both `t-1` and `t`; frame 0 has no predecessor and cannot contribute;
* the step is the **horizontal** (x-z) distance travelled between those two
  frames — `y` is excluded for the same reason
  `ardy_mlx.control.stats.displacement_m` excludes it: a lifted foot is not
  sliding, and a hop is not forward progress.

`considered` / `possible` in the table below is `planted transitions` out of
`4 × (frames - 1)`. **A clip with `considered == 0` has not been shown to be
skate-free; it has been shown to have no planted foot.** That distinction is the
reason both counts are reported.

### The two runs: postprocessing on vs off

Each action is invoked **twice**, differing in exactly one flag. This is where
the honest answer lives.

| run | flag | result |
|---|---|---|
| postprocessing **on** | *(flag omitted — the upstream Core default)* | **exit 2, no clip produced** |
| postprocessing **off** | `--no-postprocess` | exit 0, clip produced |

The refusal, verbatim, from `manifest.json → actions[*].postprocess_attempt.stderr`:

```
error: Core models run MotionCorrection by default, but the C++ extension is not
built here and contract S6.4 / decision 0002 ruling 2 pin v1 at 'both sides skip it'.
       re-run with --no-postprocess (the sidecar will record postprocess: false).
```

**This checkout cannot run ARDY's postprocessing at all.** `MotionCorrection` is a
C++ pybind11 extension (`motion_correction._motion_correction`) that is not built
here, and `docs/decisions/0002-checkpoint-terms.md` ruling 2 pins this side at
"both sides skip it" so that agreement with the golden run stays meaningful.
`scripts/ardy_generate.py` refuses rather than emitting a clip whose sidecar
would claim a policy it did not apply.

**So: the "which group is the better action asset" question has exactly one
honest answer — the only producible group is "postprocessing off", and that is
what every clip here is.** Building the extension would mean installing a
compiler toolchain and a C++ extension, which is out of scope for this task. If
that is wanted later, the measured inputs the corrector needs
(`root_positions`, `posed_joints`, `foot_contacts`) are all present in every
`npz` below.

### Measured skating (postprocessing off)

| action | skate mean (mm/frame) | skate max (mm/frame) | skate total | of planted transitions | root displacement | root path |
|---|---|---|---|---|---|---|
| `stand_idle` | **0.25** | 0.55 | 39 mm | 156 / 156 | 0.008 m | 0.012 m |
| `stand_idle_zh` | 0.32 | 0.74 | 51 mm | 156 / 156 | 0.010 m | 0.013 m |
| `crouch_idle` | **0.53** | 1.93 | 82 mm | 156 / 156 | 0.014 m | 0.031 m |
| `jump` | 0.77 | 3.62 | 84 mm | 109 / 156 | 0.032 m | 0.206 m |
| `jump_air` | 0.78 | 2.70 | 83 mm | 106 / 156 | 0.031 m | 0.226 m |
| `jump_forward` | 1.32 | 3.81 | 130 mm | 99 / 156 | **1.442 m** | 1.495 m |
| `walk` | 0.84 | 3.45 | 152 mm | 181 / 316 | **4.354 m** | 4.407 m |
| `crouch_forward` | **2.66** | 12.86 | 358 mm | 135 / 316 | 2.148 m | 2.288 m |
| `crawl_forward` | **2.74** | 9.97 | 258 mm | 94 / 316 | 1.257 m | 1.302 m |

`jump` is the one row where path ≫ displacement (0.206 m vs 0.032 m): the body
rises and returns, so it travels a fifth of a metre and ends where it started.

The two in-place baselines bound the noise floor: `stand_idle` at 0.25 mm/frame
is a figure that is declared to be standing still, so that residue is the
model's own jitter, not skating. Everything else should be read relative to it.

**Conclusion, in numbers.** At 20 fps, a metre of skating per second is
1000 mm/frame. The worst clip here — `crawl_forward` at 2.74 mm/frame — is
therefore **0.27 % of a metre per second**, i.e. the contact foot drags about
5.5 cm over a whole second. That is invisible at the scale these clips will be
played, which is the concrete reason the missing `MotionCorrection` is **not**
a blocker for shipping these six as action assets: the correction exists to
suppress millimetre-per-frame slip, and the slip here is already at that order.
Pursue it only if the clips are scaled up or the foot plant is used for
root-motion extraction, where a 1 cm drag over a second is a real error.

Skating is **not** uniform across actions: it tracks how much the action travels,
which is what you would expect (`stand_idle` 0.25 → `crawl_forward` 2.74). If a
future pass does build the corrector, `crouch_forward` and `crawl_forward` are
where it has the most to work on; the two idle clips have nothing to fix.

## 3. Quality: what worked and what did not / 生成失败的与不理想的

Reported as measured, not as hoped. Posture numbers are in
`manifest.json → actions[*].skating.posture`.

| action | verdict | evidence |
|---|---|---|
| `stand_idle` | ✅ good | hip y 0.973 m, range 0.001 m — genuinely still |
| `crouch_idle` | ✅ good | hip y held at 0.589–0.599 m for the whole clip (**−40 %** vs standing); hands at or below knee height in 100 % of frames, i.e. resting forward, not hanging |
| `crouch_forward` | ⚠️ good motion, odd posture | travels 2.148 m with hip y averaging 0.554 m and the hands reaching 0.420 m — a **deep forward-leaning squat**, plausible for a slow crouch-walk but worth eyeballing before use |
| `crawl_forward` | ⚠️ **the honest caveat: it reads as a kneel-crawl** | hip y 0.441 m, hands reach the floor (min y **0.015 m**, ≈1.5 cm), and a **knee is at or below 5 cm in 100 % of frames** (knee y min 0.009 m) — the knees, not the feet, are the load-bearing contact. Of the four `foot_contacts` channels only the two **toes** ever fire (60 % / 65 % of frames); the two heels fire **never**. It is a low hands-and-knees shuffle, not a limb-alternating crawl. It is the least convincing of the six |
| `jump` | ✅ good | leaves the ground for 9 frames (contact marker drops to `c0/4`), apex **+0.282 m** above its **start** height (hip 0.963 → 1.245 m), lands, and stays in place (root displacement 0.032 m). Hip y dips to 0.790 m at the crouch bottom — that is the *minimum*, not the start, and the +0.455 m figure is the apex above *it*; the full start → min → peak profile is in §8 |
| `walk` | ✅ good | 4.354 m forward in 4 s (1.09 m/s); mean per-frame joint motion 59 mm/frame, the largest of the six |

Two further honest notes:

1. **`walk` and `crouch_forward` start slow.** The walk's first ~35 frames
   advance millimetres per frame and the travel mostly happens in the second
   half. It is not a frozen pose — all 40/80 frames of every clip are byte-unique
   — but a clip meant to loop should be cut after the wind-up, not at frame 0.
2. **`crawl_forward` is the one to re-roll first** if the action matters. A
   different prompt or seed is the cheap experiment; this script makes that a
   one-line change (`ACTIONS` in `scripts/ardy_actions.py`).

## 4. Preview / 预览

[`preview.gif`](preview.gif) — 900×640, 3×2 grid, 40 frames @ 10 fps, 64 colours,
**971 KB**. One cell per action, each labelled with its name, prompt, frame
count, duration, and measured skating, plus a live contact count.

Each cell is rendered over the **first 40 frames** and its camera is fitted to
exactly that window, so the camera is world-fixed for what you see and

move; a camera fitted to the whole 4 s walk would have shrunk the figure to a
thumbnail instead.

Frame-by-frame geometry, and the sha256 of the GIF, are in

## 5. What each clip contains / 片段里有什么

Each `raw/<action>/ARDY-Core-RP-20FPS-Horizon40/<prompt-hash>-0.npz` is the
contract-S7 artifact from `scripts/ardy_generate.py`:

| member | shape (2 s clip) | dtype |
|---|---|---|
| `frames` | `(1, 40, 330)` | float32 |
| `posed_joints` | `(1, 40, 27, 3)` | float32 |
| `root_positions` | `(1, 40, 3)` | float32 |
| `foot_contacts` | `(1, 40, 4)` | bool |
| `offsets` | `(2,)` | int64 |
| `fps` | `()` | int32 |
| `text` | `()` | `<U…` |

4 s clips are `(1, 80, …)` with `offsets` of length 3 (two autoregressive
windows). Exact per-clip shapes, dtypes, byte sizes and sha256s are in
`manifest.json → actions[*].derived_tensors` / `.clip`.

**Units and frames.** `posed_joints` are world-space metres, Y up, ground = XZ
plane, and the Hips joint equals `root_positions` exactly (verified). They are
already forward-kinematics output, so a consumer does **not** need to re-run FK.

**Handoff.** The clips are consumed as the `.npz` above; nothing in this
directory is in a bridge-specific format. Whether the bridge wants `frames`
(the 330-D contract features) or `posed_joints` depends on the consumer, and both
are in every file.

## 6. Reproducibility / 可复现

* Every clip records its own **exact command line** in
  `manifest.json → actions[*].generated_by.command`, with repository-relative
  paths, plus its `exit_code` and `elapsed_s`.
* Every clip records the **sha256 of its `npz`, its sidecar, and the text vector
  that drove it**, so "these bytes came from this prompt" is checkable without
  re-running anything.
* The text vector's own provenance (weight digests, quantization plan, template
  regime, encoder git sha) is in
  `artifacts/embeddings/mlx-llm2vec-4-bit-group-32-last-2-layers-embed-tokens-at-8-bit/<hash>.json`,
  written by the encoder.
* Noise is MLX's RNG, not the reference's `x_T`: CUDA's Philox stream is not
  reproducible in MLX. Same seed here means same clip here, not same clip as the
  reference implementation.
* Generation is deterministic given the seed, so re-running `generate` must
  reproduce the recorded sha256s. If it does not, something changed underneath
  (weights, MLX version, prompt text) and the mismatch is the finding.

## 7. Not done / 未做

* **Postprocessing was not applied** — it cannot be, here. See §2.
* **No constraint conditioning.** All clips are unconditional text-to-motion;
  `--cfg-weight`'s constraint channel is present but unused.
* **No retargeting to the gmgn action stack's own skeleton.** These are ARDY's
  `CoreSkeleton27`, 27 joints. Any mapping onto another rig is downstream work and
  is not claimed here.
* **No long training and no synthetic input.** Every clip is one inference pass
  through the shipped checkpoint.

## 8. The jump / 跳 — this round's narrowed scope

**Why only the jump.** Crouching and crawling are *gaits*: a MotionBricks library
can already play them back from an existing style (`walk_stealth` 0.7 m/s,
`hand_crawling` 0.5 m/s, `elbow_crawling`, `stealth_walk`, …), so generating them
again would be duplicate work. A jump is a **one-shot action** — takeoff, flight,
landing — and cannot be re-timed out of a walk. It has to be generated. This
section reports only that.

### 8.1 The three prompts

All third person, matching the viewer's own vocabulary. All three use
`ARDY-Core-RP-20FPS-Horizon40`, `seed 0`, `history-frames 160`,
`diffusion-steps 10`, `cfg-weight 2.0 2.0`, `--no-postprocess`,
`duration 2.0 s = 40 frames` — which is exactly **one ARDY window** (`horizon 40`),
so each clip is a single denoising pass and cannot accumulate inter-window drift.

| name | prompt (verbatim) | role |
|---|---|---|
| `jump` | `A person jumps up in place and lands.` | the pre-existing in-place jump, kept as the comparison |
| `jump_air` | `A person jumps up in the air and lands on the spot.` | **the ask's verbatim prompt** |
| `jump_forward` | `A person jumps forward and lands.` | **the ask's forward variant** — horizontal speed across the flight |

### 8.2 Two postprocessing runs per clip / 每条跑两次后处理

Each clip is invoked twice, differing in exactly one flag.

| run | flag | result (all nine actions) |
|---|---|---|
| postprocessing **on** | *(omitted — the upstream Core default)* | **exit 2, no clip produced** |
| postprocessing **off** | `--no-postprocess` | exit 0, clip produced |

So "the two postprocessing groups" yields **one numeric row and one named
refusal**, not two sets of numbers: this checkout cannot run ARDY's
`MotionCorrection` C++ extension at all (§2). Every clip in this directory is the
`postprocess: false` group, and that is the only honest answer to "which group
should be the action asset" — the other group does not exist here.

> **Correction to a misleading field.** `manifest.json → actions[*].postprocess_attempt.produced`
> lists the files present in the model directory *after* the run, and the on-run is
> refused **after** the off-run already wrote there. So that list is the off-run's
> leftovers, **not** evidence that the refused run produced anything. Read
> `postprocess_attempt.exit_code` (2) instead. This is a known wart in
> `run_variant`'s `produced` field, left visible rather than papered over.

### 8.3 Vertical profile and landing / 竖直峰值与落地冲击

Skating (§2) answers "does a planted foot slide". A jump needs the other half:
"does it leave the ground, and how hard does it come back". Measured on the Hips
(pelvis) joint's world height, `y`, from `posed_joints`. `Hips` is a **proxy** for
the centre of mass, not a measured CoM — the contract has joint positions and no
mass distribution.

| name | airborne frames | hip y start → min → peak (m) | apex above **start** | apex above **crouch** | touchdown speed | peak descent | root displacement |
|---|---|---|---|---|---|---|---|
| `jump` | 9 | 0.963 → 0.790 → **1.245** | +0.282 m | +0.455 m | 1.92 m/s | 1.99 m/s | 0.032 m |
| `jump_air` | 10 | 0.966 → 0.786 → **1.260** | **+0.295 m** | +0.475 m | 2.09 m/s | 2.09 m/s | 0.031 m |
| `jump_forward` | 5 | 0.963 → 0.791 → **0.979** | **+0.016 m** | +0.188 m | 1.06 m/s | 1.06 m/s | **1.442 m** |

**Ballistic cross-check.** For a vertical launch that lands at the same height,
flight time `t` implies apex `g·t²/8` with `t = airborne_frames / fps`. This is an
independent physical check on the clip, not another reading of the same numbers:

| name | flight time | ballistic apex | measured apex | ratio | reading |
|---|---|---|---|---|---|
| `jump` | 0.450 s | 0.248 m | 0.282 m | **1.14** | consistent with a real jump |
| `jump_air` | 0.500 s | 0.306 m | 0.295 m | **0.96** | consistent with a real jump |
| `jump_forward` | 0.250 s | 0.077 m | 0.016 m | **0.21** | **5× short of ballistic — no real flight arc** |
| `walk` *(control)* | 0.400 s | 0.196 m | 0.006 m | **0.03** | 8 contact-free frames with no rise at all |

### 8.4 Verdict / 结论

* **`jump_air` is the jump asset.** Apex +0.295 m over the standing pose, 0.5 s of
  contact-free flight, ratio 0.96 against ballistic, lands in place (0.031 m of
  root travel), and the **lowest skating of the three jumps** (0.78 mm/frame mean,
  2.70 mm/frame max, 83 mm total). It is the ask's verbatim prompt and it is the
  best-behaved clip of the three.
* **`jump` (in place) is an equally usable alternative** — 0.282 m apex, ratio 1.14,
  0.77 mm/frame. The two in-place prompts produce near-equivalent jumps; prompt
  wording between them is not a meaningful lever.
* **`jump_forward` does NOT read as a jump, and is not recommended as one.** It
  travels 1.442 m forward — so the "keep horizontal speed through the flight" half
  of the ask *is* satisfied — but the pelvis rises only **1.6 cm above standing**.
  Its 5 contact-free frames are not a flight arc (ratio 0.21). Read plainly: the
  model produced a **crouch-and-step-forward**, not a forward jump. The honest
  summary is that the ask's two goods were not both delivered by one clip: you can
  have the in-place jump (`jump_air`) or the forward travel (`jump_forward`), not
  both.

**Metric caveat — `airborne_frames` alone proves nothing.** `walk` has 8
contact-free frames yet rises 6 mm, and its ballistic ratio is 0.03. So a frame
with all four `foot_contacts` false is *not* sufficient evidence of flight: the
contact labels also drop out during ordinary locomotion. The apex height and the
ballistic ratio are what separate flight from label dropout, which is why all
three columns are reported together.

### 8.5 What it looks like / 观感（如实）

Frame-by-frame in [`preview_jump.gif`](preview_jump.gif), `jump_air` shows a
readable **stand → crouch (frames 13–17) → extension with the arms swung back
(frame 21, both feet off the ground) → landing (frame 27)**. The crouch and the
extension are clearly present and the contact markers switch to `c0/4`.

Honest reservations: it reads as a **small, forward-leaning hop rather than a
crisp vertical jump**. The figure leans noticeably in the travel direction
throughout, the silhouette change between crouch and apex is modest, and at 20 fps
the whole flight is 10 frames, so the "air" moment is brief. It is a usable,
physically consistent jump; it is not an athletic one. `jump_forward` in the same
GIF shows the problem directly: it slides right across the cell while staying at
standing height.

### 8.6 Regenerate just the jump / 只重生成跳

```bash
cd ~/dev/ardy-mlx
./.venv/bin/python scripts/ardy_actions.py encode         # 9 prompts; adds the 2 jump ones
./.venv/bin/python scripts/ardy_actions.py generate       # 32 s: all 9 clips + both metrics
./.venv/bin/python scripts/ardy_actions.py preview-jump   # preview_jump.gif, 3x1
```

The three jump prompts live in `JUMP_ACTIONS` in
[`scripts/ardy_actions.py`](../../scripts/ardy_actions.py); changing a prompt there
and re-running the three commands above is the whole edit cycle. The jump's own
preview is a separate command on purpose: `preview` still renders the original
**3×2** grid, so adding jump variants cannot silently restage `preview.gif`.
