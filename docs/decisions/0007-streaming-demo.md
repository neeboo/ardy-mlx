# 0007 · 连续动作演示（streaming）：判据先冻结

**背景**：用户要求做"像 ARDY 官方那样的连续动作演示"。内核已经具备且**已验证**：自回归窗口循环
（4.0 s = 2 窗口对金标准 **3.54e-05**、8 s = 4 窗口 815 ms）、每一步的**末帧重定心 / 平移累积 /
`first_heading_angle` 刷新**都对着参考实现验过（`0005`）。本决定冻结**外层**要做到什么，才允许动前端与服务端。

## 机制（实现必须遵守）

1. **runahead 队列**：播放第 N 窗口的同时生成第 N+1 窗口；**播放永不等待生成**（预算：2 秒窗口 110–260 ms，约 8–18× 实时余量）。
2. **口令变更只在窗口边界生效** ✗：改 prompt → 编码（本机，~0.4 s；缓存后 0）→ **从下一个窗口开始**用新向量；
   **绝不允许**在同一窗口内拼接两套条件 ✓。
3. **状态交接**沿用已验收的窗口推进逻辑（重定心/平移累积/heading 刷新 ✓），**不得另写一套** ✓。
4. **HUD 必须显示**：缓冲深度、每窗口生成耗时、当前 prompt 版本、向量来源、量化全名 ✓。

## 预注册验收判据（先写死，之后不许放宽）

| # | 判据 | 可证伪方式 |
|---|---|---|
| 1 | **连续 ≥5 分钟零停顿**：播放不出现等待生成的空档；预热后缓冲深度始终 ≥1 个窗口 | 去掉 runahead → 必须出现可测的停顿 |
| 2 | **每个窗口接缝**位置/速度都在我们实测界内（位置量级 ≤1.383 mm 一类；root 速度比 ≤1，即不超段内 p95） | 故意错一格重定心 → 必须越界 |
| 3 | **改口令延迟** ≤ 1 个窗口 ＋ 一次编码（冷编码最坏 ≈1.4 s；热 ≈0.3 s），且**只在窗口边界**生效 | 在窗口中途换条件 → 必须被拒绝/排队，不得拼接 |
| 4 | **完全离线**：不联网、不访问参考机器（无 SSH、无到 CI 机的进程） | 断网/屏蔽 CI 机后仍必须能连续跑 |
| 5 | **可播性**：生成期间角色不停（播放与生成并行），且窗口长度严格 ＝ horizon 的整数倍 | 人为让生成变慢 → 界面必须**如实地**显示缓冲耗尽/停顿，不得静默冻结 |
| 6 | **性能记录**：每窗口生成 p50/p90、编码 p50、播放帧率、峰值 RSS，并注明 loadavg | — |

## 明确排除（不许承诺，也不许在页面上暗示）

* **加速度那一维接不平** ✗ —— 4 帧条件窗口没有加速度通道（`0005`、`VIEWER` §3/§10 已记）。
  → 页面上必须写明"位置/速度连续，加速度不保证"。
* **没有后处理** ✗ —— 我们按 `0002` 裁定不构建 `MotionCorrection`，所以**比官方 demo 更滑**（官方跑了后处理）。
  → 页面上必须写明 **"脚会轻微打滑，这是已知取舍，不是 bug"**。
* **空间约束（`--constraints`）未验证** ✗ —— 本演示不做。
* **与金标准的可比性**：本机编码器向量下的动作**不能**与金标准对齐（扩散对条件混沌，不同但同样有效）✓；
  只有"参考 bf16 向量 ＋ 参考自身 `x_T`"那一支才是对齐口径 ✓。
* 单客户端、回环、无鉴权（沿用 `VIEWER` §6 的边界）。

## 顺序要求

前端与服务端同一批文件由**一个写手**完成；须等当前前端修复轮（空 prompt 守卫 ＋ 404 噪音）结束再开工，
避免两个写手撞同一批文件 ✓。
