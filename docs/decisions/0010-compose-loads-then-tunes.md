# 0010 · `compose` ＝ "先加载那条，再调参"；`generate` 只留给真正的未知

实现轮把一个**残留缺口**交上来裁定（原文）：类型门只关掉了"**类型未知**"那一半 ✗，
**没有**关掉另一半 —— 当类型**已知**、但 `library_pick` 没选中那条时，系统仍然是
"在句子向量上生成 ＋ 调速度/幅度" ✗，而**不是去加载那个已有类型的片段** ✓。

## 现象（实测）
* 去掉两条自指条目后：`爬下前行 → generate 0.54` ✓、**`向前跳 → compose 0.77`** ✗
  （jump 类型在库里 ✓，于是允许 compose ✓，但 compose **只改"怎么演"**，不去加载 jump 的片段 ✗）。
* 用户此前已明确要求："**如果有的，直接加载**" ✓。

## 裁定
1. **`compose` 的语义改为"先加载，再调参"** ✓：当请求的**动作类型已知**且库里存在该类型的
   **vetted** 条目时，默认路径是 **`library`（加载该条 ✓）＋ 叠加 `speed`/`amplitude` 等参数** ✓；
   `compose` **不再**意味着"在句子向量上重新生成再调参" ✗。
2. **`generate` 只用于**：动作类型**未知** ✓，或库里**没有该类型的 vetted 条目** ✓。
   换言之：**能加载就加载；只有加载不了才生成** ✓✓（与"有的直接加载"和 `0009` 的 pending/vetted 一致 ✓）。
3. **参数仍必须真的生效** ✓（`0008` 的判据不变 ✓）：加载来的片段同样会被 `speed`/`amplitude` 形变 ✓，
   并且**中性参数下必须逐位等于库中那条** ✓（新增判据：`speed=amplitude=1.0` 时加载路径输出与库条目**逐位相同** ✓，
   负对照＝把参数也应用到中性情况 → 必须出现非零差异 ✓）。
4. **可测判据**：
   - 类型已知且有 vetted 条目 → 路由为 **`library`** ✓，且 `decision.action` 表明"加载了哪一条" ✓；
   - 类型已知但**无** vetted 条目（全为 `pending`）→ **`generate`** ✓；
   - 类型未知 → **`generate`** ✓；
   - 加载路径上 `speed`/`amplitude` 仍可分（沿用 `0008` 的判据 ✓）；
   - 负对照：故意把"加载"实现成"重新生成" → 判据 3 的逐位相同必须失败 ✓。
5. **`0009` 已覆盖"库必须是策展集合"** ✓：`pending`/`vetted` 状态落地后，"凡是敲过一次的句子都算已知"
   的问题随之消失 ✓ —— 本决定不再重复规定，只引用 ✓。

## 留给下一轮的顺序（Lead 排定）
1. **连续流、不 loop ＋ 客户端不重置**（轨迹累积、相机不重取景、播放头不回头 ✓ —— 用户最直接的抱怨 ✓）；
2. **库条目状态（`pending`/`vetted`）** 落地 ✓；
3. **本决定**（`compose` ＝ 加载＋调参 ✓）。
