# 0011 · 跟随相机与"页面自己的日志"

**提案（proposal）**，待裁定。本轮改了两处，都是 `0009` 留下的口子。

## 一、相机必须"跟随"，而"不重新取景"的判据要写准

**现象**（本轮）：服务端日志**完全干净** ✓ —— 48 行里 43 个 200、零 4xx/5xx、零 traceback ✓，
序列是 `GET /` → 静态资源 → `/api/health` → `/api/plan` → … ✓（页面确实在连续流 ✓）；
`segments_generated: 8`、`frames_generated: 680`（约 34 秒动作 ✓）、`continuation_active: true`、
`continue_ready: true`、`last_windows: 4` ✓；router `ok`（6 次调用、0 超时 ✓）。
**结论：服务端没有故障，问题在观感/客户端** ✓。

角色已经连续走了 **约 34 米**。而按 `0009` §二 的裁定"**相机只在第一段或点 Fit 时才取景**"✓，
实现成了"**取景一次，之后永不移动**"✗ → 相机不跟随 ✗ → 角色早在第 75 帧就走出了画面 ✓，
读者看到的是一块空地板 ✓。这**不是** `0009` 要修的"重新取景"✗：角色在**运动** ✓，相机必须跟着动 ✓。

### 裁定

1. **跟随平移** ✓：每一渲染帧把相机 `focus` 朝角色的**根位置**移动 ✓，带指数阻尼 ✓，不瞬移 ✓。
2. **跟随只改 `focus`** ✓；`distance` 与 `yaw`/`pitch` 仍**只在用户操作时变** ✓（Fit 按钮、拖拽、滚轮 ✓）。
   因此 `0009` §二 的"**没有用户操作时不得重新取景**"**原样成立** ✓。
3. **Fit 落在角色身上** ✓：`userRequested` 的 Fit 把 focus 放在角色（`followTargetNow()`）✓，
   而**开场取景**（第一段、无用户操作）落在该段的**包围盒中心** ✓。
   理由：Fit 是"我想看清角色"✓；把 focus 放到整段轨迹中心（34 米跑的**中心**离角色 10 米以上 ✗）
   会让跟随再从 10 米外追回来 ✓ —— 那是跳变 ✗，不是重新取景 ✓。
4. **判据从"相机矩阵逐位不变"改为"不得跳变"** ✓：
   * **判据 6（角色必须在画面内）** ✓：把角色**根**与其上 0.85 m 的"头"用 pinhole＋`lookAt`
     投影到 NDC ✓，**每一帧**都必须在视锥内 ✓（`margin` 全幅 ✓）。
   * **判据 7（不得跳变）** ✓：**每一帧 focus 位移 < `CAMERA_MAX_STEP_M`** ✓，
     **相机世界坐标位移** < 同阈值 ✓，且**阻尼从不触发钳位** ✓（`clamped` 一帧都不许有 ✓）。
   * **判据 8（跟随只改 focus）** ✓：结构上，跟随路径不得写 `cameraView.distance`/`yaw`/`pitch` ✓。
5. **阈值 0.5 m/帧的依据** ✓（没有依据的阈值是没人能核对的阈值）：
   * 播放按 clip 的 **20 fps** ✓ → 一渲染帧 = **0.05 s** ✓；
   * 值得画出来的最快走速 ≈ **2 m/s** ✓ → 每帧根位移 = **0.10 m** ✓；
   * 健康跟随时 focus 每帧只走 `v·dt` ≈ 0.10 m ✓，阻尼收敛速率是 `gap / τ`，
     只有在 gap 已 ≥ 3 m 时才会到 0.5 m/帧 ✓；
   * 而页面**能意外产生的最小跳变**是"按一段 clip 的包围盒重新取景"= 半段长度 ≈ **1 m** ✓。
   → 0.5 m 是**意图运动的 5 倍** ✓、且**低于最小意外跳变的 2 倍** ✓。达到或超过即判定为"跳"✓。
6. **负对照**（每条都实跑，且改坏实现后必红 ✓）：
   ① 关掉跟随 → **判据 6 红** ✓（同一段 23 m 的走，静态相机下角色第 75 帧起离开画面 ✓）；
   ② 每段调一次取景 → **判据 7 的相机位移红** ✓（焦点被扔向累计包围盒中心 +1 m/缝 ✓，
      距离 5.1 → 10.1 → 15.2 → 24（钳位）✓，相机位置单帧跳数米 ✓）；
   ③ 跟随实现成瞬时对齐 → **判据 7 的 focus 位移红** ✓（接管那一刻一步走完 1.10 m 的站立间隙 ✓，
      阻尼版同帧只走 0.168 m ✓）；
   ④ 额外补一条：跟随读错帧（永远盯第 0 帧）→ **判据 6 红** ✓（相机"完美"跟踪一个过去的点 ✓，
      角色照样走出画面 ✓）。
7. **可测形式** ✓：全部决策放进 `viewer/app.js` 的 `pure-timeline` 区（无 DOM、无 fetch、无 three.js ✓）：
   `followFocus(current, target, dt)` ✓、`followFocusInstant`（负对照 ✓）、
   `focusTargetAt`、`fitFocusFromBounds`、`fitDistanceFromBounds`、`fitPlacement`、
   `cameraPositionFor`、`projectPoint` ✓。
   投影是**手写的 three.js 等价式**（对称透视 + `lookAt` 世界 up）✓，
   这样"角色在不在画面里"能在裸 `node:vm` 里算 ✓ —— 用 three.js 算就只能在浏览器里测 ✗。

### 实测（`tests/viewer_js_guard.test.mjs`，23.4 m 的走，469 帧）

| 策略 | focus 单帧最大位移 | 相机单帧最大位移 | 钳位帧数 | 画面外帧数 | 最差 \|NDC\| |
|---|---|---|---|---|---|
| 跟随（出货） ✓ | **0.168 m** | 0.168 m | **0** | **0** | 0.483 |
| 瞬时对齐 ✗ | 1.097 m | 1.097 m | 0 | 0 | 0.442 |
| 不跟随 ✗ | 0 | 0 | 0 | **394**（第 75 帧起） | 2.2e7 |

## 二、页面自己的错误必须送到服务端

**现象**（本轮）：这一轮之所以只能**靠猜** ✗，是因为**浏览器里的报错服务端看不见** ✗。
服务端的 200 只说明"请求被回答了"✓，不说明"页面渲染正确"✗ —— 一个渲染异常和一次健康运行
在访问日志里**完全同形** ✗。

### 裁定

1. **新增 `POST /api/client-log`** ✓（仅回环 ✓，与其余路由同一白名单 ✓）。页面上报：
   * **三类事件** ✓：`window.onerror` → `error` ✓、`unhandledrejection` → `unhandledrejection` ✓、
     `console.error`/`console.warn` → 同名种类 ✓（**照样透传**到真正的 console ✓，是"add"不是"replace" ✓）；
   * 最近 **≤ 50** 条 ✓（`CLIENT_LOG_MAX_EVENTS = 50` ✓，页面队列同值 ✓）。
2. **语义化状态快照** ✓ 随每次上报同行：播放头/总帧数/段数/缓冲剩余/**是否持帧** ✓/是否在播/fps ✓/
   **当前意图版本** ✓/**最后一次 route 与概率** ✓/噪声/时长 ✓/**相机跟随统计**（帧数、钳位次数、
   单帧最大位移、用户跳变次数 ✓）/**角色屏幕坐标 NDC 与根世界坐标** ✓。
   最后两项是这段专门为"人是否走出画面"加的 ✓：从日志里能**直接读出**角色当时在画面哪个位置 ✓。
3. **服务端具名写日志、不静默丢** ✓：
   * 每条事件写成 `[ardy_viewer] client-log <kind> <text>` ✓；
   * 快照变化时写成 `[ardy_viewer] client-log snapshot <json>` ✓；
   * 被拒的批次写成 `[ardy_viewer] client-log refused <error>: <message>` ✓（并计数 ✓）；
   * 保留最近 **200** 条 ✓（`CLIENT_LOG_KEEP = 200` ✓），环形挤出的条数计入 `dropped` ✓ 而不是消失 ✓。
4. **可按名查询** ✓：`GET /api/client-log?kind=<kind>&limit=<n>` ✓；
   `/api/health` 里给出 `received` / `rejected` / `dropped` / `kept` / `last_at` / `last_kind` / `snapshot` ✓。
   kind 是**封闭词表** ✓：未知种类是**具名拒绝** ✓，不是空列表 ✗（空列表会被读成"没有"✗）。
5. **体量上限** ✓（都是具名错误 ✓）：单请求 ≤ 50 事件 ✓、单条文本 ≤ 600 字符 ✓、
   快照 ≤ 4000 字符 ✓、**整个 body ≤ 64 KiB** ✓（`client_log_body_too_large` ✓，比共享的 1 MiB 更紧 ✓）。
6. **key / 环境变量绝不入库** ✓：每一条字符串都过 `redact_client_text` ✓ ——
   ①先按**本进程** secret 形态环境变量的**字面值**打码 ✓（`*_API_KEY`/`*_TOKEN`/`*_SECRET`/… 且长度 ≥ 8 ✓）；
   ②再按**形态**打码 ✓（`ts_…`、`sk-…`、`jev_…`、`xox[abprs]-…`、`gh[pousr]_…`、`AKIA…`、`Bearer …`、JWT ✓）。
   替换文本**具名**（`[redacted:typesafe-key]` / `[redacted:env-secret]` ✓），**绝不含原值、也绝不含变量名** ✓。
   **页面侧也打一遍形态码** ✓：错误信息是页面**没写过**的文本 ✓ ——
   一次失败的 `fetch('https://…?key=…')` 会把整个 URL 放进 rejection ✓，只靠服务端就是在网络上裸奔 ✓。
   另外快照是**白名单投影** ✓（逐字段构造 ✓，绝不 spread ✓），URL **只取 path** ✓（query 是唯一可能夹带外部秘密的地方 ✓）。
7. **负对照** ✓：故意塞 `ts_test_key_do_not_use_0123456789` → **必须被打码** ✓，
   且断言 POST 响应、`GET /api/client-log`、`/api/health`、服务端 **stderr** 四处**都搜不到** ✓；
   正对照同时断言"这个 key 确实在发出去的原文里" ✓（否则泄漏检查是空转 ✓）。
   页面侧的另一条正对照：`{...state}` 这种"直接 spread"的快照**必须**带上 key ✓，
   出货的白名单版本**必须**不带 ✓。

## 四、仍不完美（写在明处）

* **判据 7 的阈值是"每帧"的** ✓，它假定渲染真的按 20 fps 走 ✓。标签页被冻住时 `dt` 会被上游钳到 0.1 s ✓，
  此时阻尼一步会走 0.28 倍间隙 ✓ → 钳位会**兜住** ✓，但 `clamped` 会计数 ✓ ——
  也就是说"钳位计数 > 0"读作"相机本来要跳，被兜住了" ✓，而不是"一切正常" ✓。
* **快照是页面自述、未经服务端验证** ✓（`note` 字段里写明 ✓）。它可以被一个坏掉的页面写错 ✗；
  但它**不能**被用来伪造服务端事实 ✓ —— 它是独立字段 ✓，不参与任何服务端判定 ✓。
* **心跳 30 s 一次** ✓（`CLIENT_LOG_HEARTBEAT_MS` ✓，且只在有 clip 在屏上时发 ✓），
  所以"读者说不太对之前"最多缺 30 s 的上下文 ✗。更密会让服务端日志变噪 ✓。
* **`at` 是整毫秒** ✓（`Math.round(performance.now())` ✓），服务端按整型校验 ✓；
  亚毫秒（`performance.now()` 的小数）在传输时被舍掉 ✗。
