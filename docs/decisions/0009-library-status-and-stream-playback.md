# 0009 · 库条目的"状态"与连续播放（不 loop）

本决定裁定两件由实测暴露出来的事。

## 一、库条目必须有状态：缓存 ≠ 可路由的库
**现象**（A 侧实测）：用户刚在页面上打过的两句「爬下前行」「向前跳」被缓存成了 embedding，
随后 `library_pick` 直接选中了它们自己（L29/L27）→ 路由判成 `library`。技术上"没错"
（库里确实有一条），但**语义上荒谬**：用户说的新话不该因为"他自己刚说过一次"就变成"库里已有"。

**裁定**：
1. **库条目带状态** ✓：至少区分 `pending`（仅缓存下来的向量／刚生成、未经审核 ✓）与 `vetted`（经过审核、
   允许被路由为"库里已有" ✓）。**只有 `vetted` 条目参与 `library` 路由与 `library_pick`** ✓。
2. `pending` 条目的正确处理：路由**照常判 `generate`/`compose`** ✓（即"这是新东西" ✓），生成出来的动作
   进**审核队列** ✓ → 审核通过才 `vetted` ✓（与既有的"词汇刻意增长"一致 ✓）。
3. `context.library_types`、`library_pick` 的候选项、以及 `known`/`motion_type_known` 的语义
   **都只基于 `vetted`** ✓；缓存里有多少 `pending` 不影响路由 ✓。
4. **可测判据**：同一句第一次说 → 路由**不得**为 `library` ✓；把它标为 `vetted` 后再说 → 才允许 `library` ✓；
   并附负对照（把 `pending` 当 `vetted` 用必须让这条判据失败 ✓）。

## 二、播放必须是连续流，不许 loop
**现象**：页面把最后一段 clip **反复循环** ✗ → 每 2 秒回到该段开头再播 ✓，加上每次新片段的
"重建 rig / 重画轨迹 / 播放头归零 / 相机重新取景" ✗，观感就是"角色被 reset 了" ✓
（而服务端证明姿态与世界坐标是连续的：换句后第 0 帧位移 **0.000 mm**、角色仍在 z≈15.4 m 处继续走 ✓）。

**裁定**：
1. **默认不 loop** ✓：按 `0007` 做**连续流**——播第 N 段时预生成第 N+1 段 ✓，新片段**追在队列后面** ✓，
   播放**永不回头** ✓。
2. **轨迹跨片段累积** ✓（不是用新片段重画 ✗）；**相机只在用户点 Fit 或没有上一段时取景** ✓；
   **播放头与位置显示连续** ✓ —— 只有用户主动 `Reload` 才允许重置 ✓。
3. **loop 保留为显式选项、默认关闭** ✓（用于"研究单段" ✓），并在界面上标明它是循环 ✗。
4. 生成跟不上时**如实显示缓冲耗尽** ✓（`0007` 判据⑤ ✓），**不许偷偷循环** ✗。
5. **可测判据**：连续 N 段播放中，**播放位置单调不回退** ✓；轨迹点数**只增不减** ✓；
   相机矩阵在无用户操作时**不变** ✓；并附负对照（重新打开 loop → "不回退"这条必须失败 ✓）。
